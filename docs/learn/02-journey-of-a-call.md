# 02 — The journey of a call

Let's follow ONE real call from the moment an app makes it to the moment the
answer comes back. This is the single most useful thing to trace, because
every feature of the library is some variation of this path.

The call we'll follow:

```kotlin
val best = extractOne(
    "new york jets",
    listOf("Atlanta Falcons", "New York Jets", "New York Giants", "Dallas Cowboys"),
    processor = ::defaultProcess,
)
// → ExtractedResult(choice = "New York Jets", score = 100.0, index = 1)
```

Below, ➜ means "calls into". Files are in
`src/commonMain/kotlin/io/github/likhithsj/kmatch/`.

---

## Stop 1 — The front door: `Extract.kt`

`extractOne(...)` lives here. For a list of plain strings it immediately
hands off to its generic twin with `keySelector = { it }` ("the text of each
item is… the item itself"). Then it does three things before any scoring:

1. **Process the query once.** `defaultProcess("new york jets")` → it's
   already lowercase, so it stays `"new york jets"`. (Stop 2 explains what
   processing does.)
2. **Prepare the scorer once.** ➜ `prepareScorer(...)` in `CachedScorer.kt`.
   This converts the query to code points a single time and pre-builds
   anything reusable, so the per-item loop doesn't redo query work for
   every choice. (For 4 items it hardly matters; for 20,000 it's the
   difference between 66 ms and 4.6 ms.)
3. **Loop over the choices**, keeping the best result seen so far.

The loop also has two smart exits:
- if a choice scores a perfect **100**, stop — nothing can beat it;
- after a good match, the required score (`currentCutoff`) rises, so later
  comparisons can give up early (stop 5 explains how).

## Stop 2 — Cleaning text: `Process.kt` + `UnicodeTables.kt`

`defaultProcess` is the standard "make text comparable" step:
lowercase everything, turn every non-letter/non-digit into a space, trim the
ends. `"New York Jets!"` → `"new york jets"`.

The twist: *which* characters count as letters, and *how* to lowercase them,
differs slightly between programming languages. To keep the RapidFuzz
promise, kmatch doesn't trust the platform — it uses lookup tables in
`UnicodeTables.kt` that were generated by literally asking RapidFuzz's own
engine, character by character (`tools/generate_unicode_tables.py`).

## Stop 3 — From text to numbers: `CodePoints.kt`

Computers store text as UTF-16 units, where an emoji is secretly TWO units.
Comparing those directly gets Unicode wrong (a single 😀 would look like two
"letters"). So the first real transformation is:

```
"new york jets"  ➜  IntArray: [110, 101, 119, 32, 121, 111, 114, 107, ...]
```

one integer per *actual character* (code point). Every algorithm below this
line works on these integer arrays, never on `String`. This is why emoji,
Chinese, Arabic, etc. all score correctly.

## Stop 4 — Choosing a strategy: `Fuzz.kt`

Our call used the default scorer, `weightedRatio` ("WRatio"). Think of it as
a *router*: it looks at the two strings and decides which comparison styles
are worth running.

For query `"new york jets"` (13 chars) vs choice `"new york jets"`
(processed from "New York Jets", also 13 chars):

- lengths are similar (ratio < 1.5), so it runs:
  - a plain whole-string comparison → `ratioCps(...)`
  - word-based comparisons (ignore word order / extra words) → `tokenRatioCps(...)`
- and keeps the best answer.

(If the choice had been much longer than the query — like a query against a
long product title — WRatio would instead bring in the "sliding window"
comparison, `partialRatioCps`. File 03 covers each style.)

All of these styles eventually need the same primitive: *how many edits
apart are these two code-point arrays?* That's the ground floor.

## Stop 5 — The engine room: `Indel.kt`

`indelNormalizedSimilarity(a, b, cutoff)` computes the score in three steps:

1. **Cheap escape hatch first.** The best case is limited by length: if one
   string has 5 characters and the other has 50, at least 45 edits are
   unavoidable. If even that best case can't reach the cutoff, return 0.0
   *without comparing anything*. This is how high cutoffs make searches
   faster.
2. **Count the longest common "backbone"** — the longest sequence of
   characters appearing in both strings in the same order (the LCS). This
   is THE expensive step, and it's done with the bit-parallel trick
   (file 04). For our identical 13-character strings: backbone = 13.
3. **Turn it into a score:**
   ```
   edits = lenA + lenB − 2 × backbone  =  13 + 13 − 26  =  0
   score = 1 − edits ÷ (lenA + lenB)   =  1 − 0          =  1.0  → 100
   ```

## Stop 6 — Back up the stack

- `Indel.kt` returns `1.0` ➜ `Fuzz.kt` scales it to `100.0`
- ➜ the loop in `Extract.kt` sees 100, remembers
  `ExtractedResult("New York Jets", 100.0, index = 1)`, and — because 100 is
  unbeatable — stops looping entirely (Dallas Cowboys never gets scored!)
- ➜ your app receives the result.

## The same journey, with visible math

Identical strings make a boring trace, so here's the full arithmetic for a
small real one — `Fuzz.ratio("cat", "cart")`:

```
"cat"  ➜ [99, 97, 116]          (c, a, t)
"cart" ➜ [99, 97, 114, 116]     (c, a, r, t)

backbone (LCS): c, a, t appear in both, in order  → 3
edits  = 3 + 4 − 2×3 = 1        (insert the 'r')
score  = 100 × (1 − 1/7) = 85.714285…
```

Run it yourself in the playground — it prints exactly `85.71428571428571`.
